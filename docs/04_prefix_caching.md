# 04 · 前缀缓存（Prefix Caching）

## 1. 问题：大家的开头经常一样

真实应用里，很多请求的开头是**完全相同**的：

- 同一个产品的所有用户共用一段很长的**系统提示词（system prompt）**。
- 多轮对话：第 2 轮的输入 = 第 1 轮的全部内容 + 新问题。
- 同一篇文档上问多个问题（RAG、few-shot 示例）。

如果每个请求都从头算一遍这段相同的开头，就是大量重复劳动。

## 2. 思路：相同的块只算一次

有了分页（paging）之后，事情变得简单：KV 缓存本来就是一块一块的，**如果两个请求的某一块内容完全一样，就让它们的块表指向同一个物理块。**

**比喻**：全班同学的作文都要先抄同一段题目。第一个同学抄完后，老师把那页复印件贴在公告栏上；后面的同学直接在自己的页码清单里写"第 1 页 = 公告栏那页"，不用再抄了。

## 3. 怎么判断"两块一样"？哈希链（Hash Chain）

只比较这一块的 16 个 token 是不够的。因为 KV 值依赖于**前面所有的 token**（注意力会回头看）。"今天天气很好"里的"很好"，和"他的成绩很好"里的"很好"，K/V 完全不同。

所以每个**写满的块**的哈希这样算（`block_manager.py` 里的 `compute_block_hash`）：

```
hash(第 i 块) = hash( hash(第 i-1 块), 第 i 块的 16 个 token )
```

哈希一路串起来，**哈希相同 ⇔ 从开头到这一块的所有 token 都相同**。块管理器维护一张表 `hash_to_block_id: 哈希 → 物理块号`。

为了防止极小概率的哈希碰撞（hash collision），命中后还会再比较一次 token 本身是否相同。

## 4. 共享就需要引用计数（Reference Count）

一个物理块可能同时被好几个请求使用。每个块有一个 `ref_count`：

- 分配给一个请求：`ref_count += 1`
- 一个请求结束：`ref_count -= 1`
- **只有降到 0，块才真正变空闲**。

这样一个请求结束不会把别人还在用的块释放掉。

## 5. 释放了也先别忘：LRU 复活

`ref_count` 归零的块进入空闲队列，但**内容和哈希都保留**。如果后来有请求的哈希命中了它，就直接把它从空闲队列里拿回来继续用（"复活"）。只有当空闲块不够、它被分配给别的内容时，才会真正被覆盖，那时才把它的哈希从表里删除。

空闲队列按 LRU（最久未使用先淘汰）排序；请求结束时**倒序**释放块，这样尾部（个性化内容）先被淘汰，开头（共享前缀）留得更久。

## 6. 几个容易出错的细节（面试加分点）

1. **只缓存写满的块**。最后一块没写满，后面 decode 还会往里写新 token，不能共享。
2. **至少要算最后一个 token**。如果整个 prompt 都命中缓存，我们就没有 logits 去采样第一个新 token 了。本项目的处理：如果命中的是 prompt 的最后一块（而且正好写满），就把它当作未命中，重新算这一块。见 `allocate()` 里的 `is_last_full_block`。
3. **decode 生成的 token 也会被登记**。块在 decode 中被写满时（`may_append`），也计算哈希登记。所以多轮对话的下一轮，连上一轮模型的回答都能命中缓存。
4. **同一个 batch 内也能共享**。两个开头相同的请求同时 prefill：第一个请求分配块并登记哈希，第二个立刻命中。这能成立是因为每一层注意力都是先把整个 batch 的 K/V 写进缓存（`store_kv`），再计算注意力，所以第二个请求读的时候，数据已经写好了。
5. **命中后注意力怎么算**：命中部分不再计算，只算剩下的新 token（query 少于 key）。因果掩码要"右下对齐"：第 j 个新 token 的绝对位置是 `已缓存长度 + j`，它能看到 0 到这个位置的所有 key。见 `attention.py` 的 `_prefill_attention`。
